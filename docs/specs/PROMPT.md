> **How to use this file:** put it in the root of an empty repo as `PROMPT.md`. In your coding tool (Cursor, Claude Code, Windsurf, etc.), say: *"Read PROMPT.md fully. Build Phase 1, then stop and show me."* Continue phase by phase. Dictate your follow-ups with Wispr Flow.

## 0. Your role

You are a senior full-stack engineer and product designer who has shipped incident-response tooling. You are building **TraceTalk**, a voice-first investigation notebook for security analysts, as a solo hackathon project with a hard deadline. Prefer working, simple, well-structured code over clever abstractions. Do not add features that are not in this document. When something is ambiguous, pick the simplest option that satisfies the acceptance criteria and note it in `DECISIONS.md`.

## 1. Product in one paragraph

An analyst investigating an incident has logs open and wants to narrate findings without switching to a notes app. They hold their dictation key (Wispr Flow) and say: *"At 14:32 the host made an unusual outbound connection. The process was launched by PowerShell. We haven't confirmed data exfiltration yet."* TraceTalk splits that into separate ledger entries (facts, hypotheses, unknowns), links each fact to the exact log events that support it, flags anything that contradicts the logs or earlier notes, and produces an incident report where every claim cites its evidence. **The core principle: the system never invents findings. It only structures what the analyst said and checks it against evidence.**

## 2. Hard constraints (hackathon)

- Live public URL. **No login, no signup.** A judge must see a fully loaded sample case within 10 seconds of opening the link.
- Case `IR-2026-0147` (Section 9) is preloaded on first visit. A "Reset demo case" action restores it.
- Must work without any API key, using the offline rule-based parser (Section 7.6). The model-based parser is used when a key is configured.
- Typing must work everywhere. Voice is an input method, not a requirement.
- Deploy on Vercel. Everything else runs client-side except the `/api/parse` route.

## 3. Tech stack

- Next.js (App Router) + TypeScript (strict) + Tailwind CSS.
- State: Zustand with `persist` middleware (localStorage), one store per case, keyed by case ID.
- Virtualized table for the timeline: `@tanstack/react-virtual`.
- Icons: `lucide-react`, 16px, stroke 1.5. No other icon sets.
- Fonts via `next/font/google`: **IBM Plex Sans** (UI) and **IBM Plex Mono** (log data).
- Model calls: one server route `app/api/parse/route.ts` using an **OpenAI-compatible chat completions API**, configured by env vars `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`. This works with Groq, OpenRouter, Gemini's OpenAI-compatible endpoint, etc. Request JSON output. If the env vars are missing or the call fails, fall back to the offline parser and show a small status note in the capture bar: "Offline parser".
- No database. No auth. No analytics.
- Validate all model output with `zod`. Invalid output → retry once → offline fallback.

## 4. Data model (`lib/types.ts`)

```ts
type SourceType = "sysmon" | "winsec" | "proxy" | "defender";

interface LogEvent {
  id: string;            // "EVT-0017"
  timestamp: string;     // ISO 8601 UTC
  source: SourceType;
  host: string;
  event_id: number | string;
  raw: Record<string, unknown>; // the full original JSON line
  summary: string;       // one-line, generated by summarize() in lib/summarize.ts
}

type EntryKind = "fact" | "hypothesis" | "unknown";
type FactStatus = "confirmed" | "unverified"; // only for kind === "fact"

interface EvidenceLink {
  eventId: string;
  relation: "supports" | "contradicts" | "related";
  matchedFields: { field: string; value: string }[]; // must exist verbatim in event.raw
}

interface LedgerEntry {
  id: string;              // "OBS-001", "HYP-001", "UNK-001"
  kind: EntryKind;
  status?: FactStatus;
  text: string;            // normalized statement, analyst's meaning, first person removed
  eventTime?: string;      // ISO UTC the claim is about, if any
  noteId: string;          // the dictated note it came from
  evidence: EvidenceLink[];
  createdAt: string;
  resolvedBy?: string;     // for unknowns: entry ID that answered it
  analystEdited: boolean;
}

interface Note {             // the raw dictation, kept verbatim forever
  id: string;                // "NOTE-004"
  text: string;
  createdAt: string;
  pinnedEventIds: string[];  // timeline rows selected when the note was captured
  parser: "model" | "offline";
}

interface Contradiction {
  id: string;                // "CON-001"
  kind: "claim_vs_evidence" | "claim_vs_claim";
  entryId: string;
  againstEntryId?: string;
  againstEventId?: string;
  explanation: string;       // one sentence, factual, cites field values
  state: "open" | "resolved" | "dismissed";
  resolutionNote?: string;
}

interface Case {
  id: string; title: string; severity: "low" | "medium" | "high" | "critical";
  status: "open" | "contained" | "closed";
  analyst: string; timezone: string; // timezone used to interpret spoken times
  caseDate: string;                  // YYYY-MM-DD, used to resolve "at 14:32"
  events: LogEvent[]; notes: Note[]; entries: LedgerEntry[]; contradictions: Contradiction[];
  activity: { at: string; actor: "analyst" | "system"; text: string }[]; // audit trail
}
```

## 7. Core logic

### 7.1 Ingestion and summaries (`lib/ingest.ts`, `lib/summarize.ts`)

Parse JSONL, validate required fields (`id`, `timestamp`, `source`, `host`, `event_id`), keep the full object in `raw`. Generate summaries deterministically per source and event ID:

- sysmon 1: `{basename(Image)} started by {basename(ParentImage)} — {CommandLine truncated to 90 chars}`
- sysmon 3: `{basename(Image)} → {DestinationIp}:{DestinationPort} ({DestinationHostname})`
- sysmon 10: `{basename(SourceImage)} opened {basename(TargetImage)} (access {GrantedAccess})`
- sysmon 11: `{basename(Image)} created {TargetFilename}`
- sysmon 22: `{basename(Image)} resolved {QueryName} → {QueryResults}`
- winsec 4624/4625/4648: logon success / failure / explicit credentials, with user, type, source IP
- proxy: `{method} {dest_host}{path} · out {bytes_out} · in {bytes_in}`
- defender 1116/1117: `Detected {ThreatName} at {Path} / Action: {ActionName}`

### 7.2 The parse pipeline (`/api/parse`)

Input: note text, pinned event IDs, case timezone and date, current ledger (id, kind, text, evidence IDs), and candidate events.

1. **Candidate retrieval (client-side, deterministic, before calling the server):**
   - Pinned events always included.
   - Extract times from the note (`14:32`, `14:32:07`, `2:32 pm`) and resolve against `caseDate` + `timezone` to UTC; include events within ±90 seconds.
   - Extract entities: IPs, domains, ports, file names (`*.exe`, `*.dll`, `*.rar`, `*.docm`), hostnames, usernames, and keyword-to-process aliases (`powershell` → `powershell.exe`, `word` → `WINWORD.EXE`, `outlook` → `OUTLOOK.EXE`, `rundll` → `rundll32.exe`, `lsass`, `defender`, `proxy`). Phrases like `outbound connection`, `connected to`, `beacon` also match sysmon event 3 and proxy events; `DNS`, `resolved` match sysmon 22; `logon`, `login` match winsec events.
   - A sentence with no time of its own inherits the last time mentioned earlier in the same note.
   - Include events whose raw JSON contains any entity (case-insensitive).
   - Cap at 25 events, ranked: pinned > time match + entity match > time match > entity match. Send compact versions (id, timestamp, source, event_id, and the raw fields only).
2. **Model call** with the system prompt in 7.3. Response must match the zod schema in 7.4.
3. **Server-side validation (the integrity guarantee):**
   - Every `eventId` must be in the candidate set.
   - Every `matchedFields` value must appear verbatim (case-insensitive substring) in `raw[field]` of that event. Drop any link that fails. Log dropped links to the activity trail as "1 evidence link rejected: value not found in EVT-00xx".
   - A `fact` with at least one valid `supports` link → `confirmed`. Without → `unverified`.
   - Contradictions must reference a valid entry and a valid event or prior entry; otherwise drop.
4. Return entries, contradictions, and answered-unknown links. Client assigns IDs and stores everything, including the verbatim note.

### 7.3 System prompt for the parser (put in `lib/prompts.ts`, use verbatim)

```
You structure a security analyst's spoken investigation notes into an evidence ledger.

You receive: the analyst's note (verbatim dictation, may contain filler words), the case timezone and date, the current ledger, and a set of candidate log events (JSON).

Rules:
1. Never add findings the analyst did not state. Your job is to split, classify and link, not to investigate. If the logs show something interesting the analyst did not mention, do not create an entry for it.
2. Split the note into atomic statements. One claim per entry.
3. Classify each statement:
   - "fact": the analyst states something as observed or true ("the host connected to…", "PowerShell launched rundll32").
   - "hypothesis": the analyst signals belief or inference ("probably", "looks like", "I think", "likely", "could be", "suggests").
   - "unknown": an open question or something explicitly not yet confirmed ("we haven't confirmed…", "not sure whether…", "need to check…").
4. Rewrite each statement as a short, neutral, third-person sentence that keeps the analyst's meaning. Keep exact technical values (IPs, process names, times).
5. Resolve spoken times using the case timezone and date. Output eventTime as ISO 8601 UTC, or null.
6. For each entry, link candidate events:
   - "supports": the event's fields directly show what the statement claims.
   - "contradicts": the event's fields directly show the opposite.
   - "related": relevant context, neither proving nor disproving.
   For every link, list matchedFields: the exact field name and an exact substring of its value from the event JSON. Only use values that literally appear in the event. If you cannot quote a value, do not link the event.
7. Hypotheses and unknowns may have "related" links; an unknown may list events that could answer it as "related".
8. Contradictions:
   - claim_vs_evidence: a statement conflicts with a candidate event. Explain in one sentence citing the field and value.
   - claim_vs_claim: a statement conflicts with an existing ledger entry. Explain in one sentence.
   Do not flag differences in wording or precision as contradictions.
9. If a new statement answers an existing unknown, return its ID in answersUnknownIds.
10. Output only JSON matching the schema. No prose, no markdown.
```

### 7.4 Output schema (zod)

```ts
const ParseResult = z.object({
  entries: z.array(z.object({
    tempId: z.string(),
    kind: z.enum(["fact", "hypothesis", "unknown"]),
    text: z.string().min(3).max(300),
    eventTime: z.string().nullable(),
    evidence: z.array(z.object({
      eventId: z.string(),
      relation: z.enum(["supports", "contradicts", "related"]),
      matchedFields: z.array(z.object({ field: z.string(), value: z.string() })).min(1),
    })),
    answersUnknownIds: z.array(z.string()).default([]),
  })),
  contradictions: z.array(z.object({
    kind: z.enum(["claim_vs_evidence", "claim_vs_claim"]),
    entryTempId: z.string(),
    againstEventId: z.string().nullable(),
    againstEntryId: z.string().nullable(),
    explanation: z.string().max(240),
  })),
});
```

### 7.5 Re-checking

When events are imported or an entry is edited, re-run contradiction checks for affected entries (send only those entries plus candidates). Show a small "Recheck" button on each entry as well.

### 7.6 Offline parser (`lib/offlineParser.ts`)

Deterministic fallback so the live demo never breaks:
- Split on sentence boundaries. Drop fragments shorter than three words ("Confirmed.", "Okay so.").
- Classify: hedge words (`probably, likely, maybe, might, could, seems, looks like, i think, suspect, suggests`) → hypothesis; negation/uncertainty patterns (`haven't confirmed, not confirmed, unclear, unknown, need to check, not sure, whether`) → unknown; else fact.
- Link evidence using the candidate retrieval results: an event "supports" a fact if it matches the resolved time (±90s) **and** at least one entity, with `matchedFields` taken from the fields where the entity was found.
- Built-in contradiction rules: (a) fact says process X was launched/started/spawned by Y, but a pinned or candidate sysmon 1 event whose Image is X has a ParentImage whose basename isn't Y; (b) fact claims no data left / no exfiltration / nothing uploaded, and any proxy event in the case has `bytes_out > 10,000,000`; (c) two facts attribute different destination IPs to the same process name.
